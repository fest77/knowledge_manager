### 3.1 权限判定刻意不走 `@require_perm`（本模块独一份）

| 码 | 条件 | HTTP |
|---|---|---|
| `MET-2002` | 有 JWT 但无 `metric:read`（如提问者 `wangqiang`） | 403 |
| `MET-2003` | **知识管理员**（`kb_admin`，原型 `08` 矩阵画「—」） | 403 |
| `MET-2005` | 有 `metric:read` 但无 `metric:export` | 403 |
| `MET-2004` | > 60 次/分钟/用户（R-11） | 429 |

为什么不用全局的 `enforce_perm`：它只会产出 `AUTH-2004`（01 的码，"你没有这个权限"）。
而 `MET-2003` 要表达的是**"这个页面本就不对知识管理员开放"**——两者对用户的含义不同，
且 AC-09-14 明确要求"必须显式拒绝，不得返回空数据"。**认证**仍由 JWT 中间件负责（ER-08），
所以本模块**不定义也不抛出**任何 401 码（OQ-09-08 的裁定）。

## 四、数据模型（E20 `metric_buckets`）

### 4.1 桶主键与字段

| 字段 | 说明 |
|---|---|
| `_id` | `"{bucket_type}:{bucket_key}:{ts}"`（ts 是**对齐后**的 epoch 秒） |
| `bucket_type` / `bucket_key` | `global`(`all`/`uv`) / `faq`(FAQ 编号) / `latency`(7 个区间标签) / `doc`(文档编号) |
| `granularity` | `1m` / `1h` / `1d` |
| `bucket_ts` | 对齐后的秒（**与 `_id` 里的 ts 同值**，但必须独立成字段，见 §六 的 bug ①） |
| `metrics` | **只放可加计数**：`pv / question_cnt / faq_hit_cnt / rag_cnt / no_knowledge_cnt / token_prompt / token_completion / elapsed_sum_ms / denied_chunk_cnt` |
| `uv_set` | **仅 `1d` 桶**：去重用户 ID 集合（`$addToSet`）。AD-12 的核心载体 |
| `expire_at` | **仅 `1m`/`1h` 桶**：`bucket_ts + 30 天`；`1d` 桶**不写**这个字段 |

### 4.2 索引

| 索引 | 键 | 用途 |
|---|---|---|
| `ix_metric_query` | `bucket_type + granularity + bucket_ts` | 看板主查询（趋势/概览/延时） |
| `ix_metric_drill` | `bucket_type + bucket_key` | 单维度下钻（某 FAQ / 某文档的历史曲线） |
| `ttl_metric_short` | `expire_at`（`expireAfterSeconds=0`）+ **部分索引** `granularity ∈ {1m,1h}` | 分钟/小时桶 30 天自动清理，**日桶永久** |

TTL 为什么用「双字段 + 部分索引」：Mongo 的 TTL 索引只能基于一个日期字段，
而"按粒度分支保留"没有别的表达方式。替代方案是两个集合，代价是查询要跨集合 union。

### 4.3 降采样策略（AC-09-12 的全部秘密）

| 查询跨度 | 读取粒度 | 最多读多少桶 |
|---|---|---|
| ≤ 1 天 | `1m` | ≤ 1440 |
| 1 天 ~ 7 天 | `1h` | ≤ 168 |
| > 7 天 | `1d` | ≤ 366 |

三条硬约束：

1. **只选一个覆盖整个区间的最细粒度**（不做"分段各选粒度再拼接"，那会在边界重复计数）
2. **一次 `find()` 取全部桶**（168 个桶逐个查就是 168 次往返）
3. **绝不读 `1m` 去画 30 天**：那要拉 43200 个文档，比不降采样还慢；客户端点名 `1m` 跨多天 → `MET-1005`

### 4.4 桶缺失时的三种降级（Spec §7.2 第 3 项）

| 场景 | 行为 |
|---|---|
| 自动选粒度 + 该粒度无桶 | **回退读更细的桶现算汇总**（保持 `x_axis` 契约不变），回 `degraded:true` + `source_granularity` |
| 客户端点名 `1h`/`1d` 且无桶 | `MET-3002`（409）——点名要粗粒度却静默返回零值就是"少算" |
| 需要 `1m` 桶但已过 30 天 TTL | `MET-3003`（410）——没有更粗的桶可回退，唯一诚实的回答是"数据过期" |

`downsampled` = "这次用了比分钟更粗的粒度"；`source_granularity` = **实际读的桶粒度**。
两个字段一起回显，是为了让"为什么这屏标了降级"可解释，而不是让人去猜。

### 5.1 06→09 投递的落地细节（AC-09-06 / AC-09-07）

- 投递发生在**落库之后**、且外面再包一层 `try`：指标是旁路，绝不能因为它失败去回滚用户已看到的答案
- `MetricService.inc()` 自身也**吞掉所有异常**（只记 `MET-5001`），异常不外抛给 06
- `doc_ids` 取 **放行列表**（`allowed`）去重后的 `doc_id`，不是最终引用列表——与 Spec §4.1 第 6 步一致
- 取不到 `user_id` 时**跳过 UV 写入并记 WARN**：写 `null` 会让集合里多一个"匿名用户"，把 UV 永久抬高到 ≥1

### 6.1 测试逼出来的三个真 bug

**① `inc_bucket` 少写了 4 个索引字段（最严重）**

`$setOnInsert` 只写了 `created_at`，而 `bucket_type` / `bucket_key` / `granularity` / `bucket_ts`
**只存在于 `_id` 字符串里**。查询侧走的是 `ix_metric_query`（按这三个字段过滤），
所以症状是：**写进去了、按 `_id` 查得到、看板却全零**。
按 `_id` 查（`get_bucket`）是查得到的——这也是它最容易被漏掉的原因。
修复：把 4 个字段放进 `$setOnInsert`（Spec §4.3 的示例代码本来就带着它们）。

**② `asked_at` 是毫秒，而区间是秒：右端被截掉最多 999ms**

`_resolve_range` 把区间统一成**秒**（桶的 `bucket_ts` 是秒），再 `× 1000` 去比 `qa_logs.asked_at`
就会漏掉"当前这一秒"里已经发生的日志。症状是"刚刚问的那一条不在榜单里"、
"近 1 天的精确分位少一条"——而且**越新的数据越容易丢**，看起来像随机丢数据。
修复：`_qa_match()` 把右端补齐到 `end_s * 1000 + 999`。

**③ 回退逻辑无条件读更细的桶**

`_metric_series` 原本无论粗桶是否命中都会继续读 `1h`/`1m`：
既浪费（AC-09-12 要钉死的正是这个），又会在 `alt` 非空时**覆盖**已经取到的正确粒度。
修复：只在 `not rows` 时才进入回退链。

### 6.2 一条测试纪律

`MetricService` 是**模块级单例**，缓存与限流计数活在进程里，`client` 夹具 drop 掉的是集合。
所以本模块测试用例自带 autouse 夹具 `_reset_metric_singleton`——
少了它，上一个用例查过的区间会让下一个用例拿到缓存结果（症状是"数据明明灌进去了却查不到"）。

## 八、设计决策与遗留事项（登记，不是 TODO）

| 编号 | 决策 | 理由 | 代价 |
|---|---|---|---|
| **DEC-09-1** | **不做内存写队列**（Spec §4.1 的"批量 flush 1s/50 条"），改为直接写 4~6 个 `_id` upsert | ① `inc()` 由 06 的**落档异步任务**调用，不在 SSE 关键路径上；② 队列会引入"进程退出即丢指标"的窗口，与 AC-09-06"1 秒内可见"相冲突；③ 每条问答只多 4~6 次主键 upsert（<1ms） | 突发问答时写入更密；将来若成为瓶颈，可退回队列并接受丢数窗口 |
| **DEC-09-2** | 热门知识榜首数据源用 **`doc` 维度桶**（退路 `qa_logs.recalled_chunks`） | 冻结的 `qa_logs.allowed_chunks` **只存 `chunk_id`**（不存 `doc_id`），按 Spec 措辞反查要逐条回 Milvus（ER-13 禁止）；而 `inc()` 已把被引用的 `doc_id` 累进 `doc` 桶 | 与 Spec §3.4 字面措辞有偏差；已在代码注释与本表登记 |
| **DEC-09-3** | 导出**未**落 `audit` 事件（Spec §3.5 R-5 标为"可选"） | AUDIT §2.2.3 的 12 个 `target_type` 里没有 `metric` 类，新增会改动已冻结的 10 模块契约；而该留痕在 09 里本就是可选 | 导出行为没有审计留痕（`metric:export` 权限本身仍有 JWT + 权限双重约束） |
| **DEC-09-4** | 看板图表**零依赖自绘 SVG**，不引公网 ECharts | D-01 要求用**本地 vendor**，而仓库里没有 `web/vendor/echarts.min.js`；引 CDN 违反"企业内网不依赖公网" | 图表能力有限（折线/堆叠面积/直方图三种）；补上 vendor 后替换 3 个函数即可 |
| **DEC-09-5** | `1h→1d` 汇总回看 **31 天**（`1m→1h` 仍按 Spec 回看 6 小时） | 日桶要看板最长查询跨度；744 条小时桶的读取成本可忽略。**包含当前未走完的窗口**，否则"刚问的那一分钟"要等下一个整点才出现在趋势图最后一格 | 每次汇总多读几百条文档 |
| 遗留 | AC-09-13（P95 < 500ms）未做压测脚本 | 属性能验收，需真实数据量与 locust/ab 之类工具 | 演示环境数据量下无风险 |
| 遗留 | Milvus 未与 Mongo 一样"按模块隔离集合" | 测试共用 `kb_chunks_v2`，靠用例内 `drop_chunks_of(doc_id)` 预清理 | 已知项（模块 04 起） |
