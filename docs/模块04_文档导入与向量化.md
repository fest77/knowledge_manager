## 三、接口契约

### 3.1 `POST /api/v1/import/upload` — 单文件上传

| 项 | 内容 |
|---|---|
| 功能权限 | `doc:upload` |
| 请求 | `multipart/form-data`：`file`(必) / `category_id` / `title` / `auto_enable`(默认 true) |
| 出参 | `{doc_id, task_id\|null, reused, file_hash, file_ext, file_size, stage, progress, duplicated_of}` |
| HTTP | 新文件与命中复用**都返回 200**（统一契约只有 `code:0`；进度靠 `task_id` 轮询） |

**关键语义**：`upload` 阶段在**请求内**完成（校验 → 流式落盘 → 建台账 → 建任务），
其余五个阶段丢后台。这样"落盘失败"不会产生台账孤儿记录，而接口能立刻回 `doc_id`。

### 3.2 `POST /api/v1/import/batch` — 批量 / 文件夹

| 项 | 内容 |
|---|---|
| 功能权限 | `doc:upload` |
| 请求 | `files[]`(必) / `relative_paths[]` / `category_id` / `auto_map_category` / `auto_enable` |
| 出参 | `{batch_id, total, accepted, reused_count, rejected[{file_name,code,message}], items[]}` |
| HTTP | **部分成功返回 200**；**仅当全部被拒**才 400（`code` 取第一条失败项） |

### 3.3 ~ 3.7 其余五条

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/import/tasks/{task_id}` | `doc:read` | 进度：`stage_index` / `stage_total`(固定 6) / `done_stages` / `durations` / `degraded[]` |
| GET | `/api/v1/import/tasks` | `doc:read` | 队列：`?doc_id=&status=&stage=&batch_id=&page=&page_size=`（上限 200） |
| POST | `/api/v1/import/tasks/{task_id}/cancel` | `doc:upload` | 协作式取消，返回 `cancel_pending=true` |
| POST | `/api/v1/import/tasks/{task_id}/retry` | `doc:upload` | 新建任务（`retry_of`），`from_stage` 默认 `pdf_to_md` |
| GET | `/api/v1/import/docs/{doc_id}/chunks` | `doc:chunk` | 切片预览：`?page=&page_size=&keyword=&full=` |
| GET | `/api/v1/import/files/{object_key}` | `doc:read` | **对象读取 + 越界保护**（见下） |

### 3.8 `GET /api/v1/import/files/{object_key:path}` — 为什么它不在 §3.9 的表里

Spec §3.9 列了 7 条接口，但 §2.2 的「越界保护」与 **AC-04-24** 明确要求
"任何读写对象前校验对象键属于 `{doc_id}/` 前缀，否则拒绝（`IMP-2002`）"。
**没有读对象的入口，这条规则既没有落点、也无法构造越界请求去验收**，
所以补了这一条最小形态：只读、按 `{doc_id}/` 前缀鉴权、复用 `doc:read`
（**不新增权限码**，ER-09）。

前缀校验有三条规则，缺一不可：

| 规则 | 挡住的攻击 |
|---|---|
| 非空、不以 `/` 打头、不含 `..` 与 `\` | 路径穿越（`..%2fetc%2fpasswd`） |
| 第一段必须匹配 `^DOC\d{14}$` | 拿一个"看起来像路径"的键去探别的目录 |
| 该 `doc_id` **必须真实存在**（查 E04） | 伪造 `DOC20260101000001/whatever` 读取无归属内容 |

## 四、数据模型

### 4.1 E01 `kb_chunks_v2`（Milvus）— 本轮补齐了 4 个字段

Spec §2.1 的字段表里有 `title` / `parent_title` / `file_title` / `part`，
**早期骨架只建了 6 个字段**（`chunk_id`/`doc_id`/`chunk_index`/`content`/`dense`/`sparse`/`enabled`），
本轮补齐并**重建了集合**（Milvus 不能改已存在字段的类型，且当时无业务数据）。

最终 11 个字段（`enable_dynamic_field=False`，全部显式声明）：

| 字段 | 类型 | 索引 |
|---|---|---|
| `chunk_id` | INT64（auto_id，主键） | — |
| `doc_id` | VARCHAR(64) | **INVERTED** |
| `chunk_index` | INT64 | — |
| `content` | VARCHAR(65535) | — |
| `title` / `parent_title` / `file_title` | VARCHAR(65535) | — |
| `part` | INT64 | — |
| `dense_vector` | FLOAT_VECTOR(1024) | AUTOINDEX / COSINE |
| `sparse_vector` | SPARSE_FLOAT_VECTOR | SPARSE_INVERTED_INDEX / IP |
| `enabled` | BOOL | **INVERTED** |

⚠️ **`upsert` 是整实体替换**：`set_enabled()` 的 read-modify-write 必须取回
**全部**字段（抽成 `ALL_FIELDS` 常量）。少取一个字段，那次启停就会把它**悄悄写成空值**
——症状是"启停文档后，切片预览的标题列全空了"。

### 4.2 E06 `kb_import_tasks`（Mongo）

3 个索引（`status+created_at` / `doc_id` / `retry_of` 稀疏），**刻意不建 TTL**：
任务记录是排查依据，过期删除会让"上周那次为什么失败"永远查不到。

### 4.3 切片装配口径（§2.6，逐字落实）

| 字段 | 口径 |
|---|---|
| `content` | **`f"{title}\n\n{body}"`** —— **不 `.strip()`**，AC-04-12 判定的是逐字相等 |
| `title` / `parent_title` / `file_title` / `part` | 切分锚点原样落库 |
| `chunk_index` | 按输出顺序从 0 连续递增 |
| `enabled` | **一律先写 `false`**，由 `mark_import_done()` 按 `auto_enable` 统一同步（理由见 §6.2） |

## 五、六阶段与失败处理

### 5.1 阶段与进度权重

| # | 阶段 | 进度 | 实现要点 |
|---|---|---|---|
| 1 | `upload` | 0 → 10 | **请求内**：流式 SHA256 + 落盘 + 建台账 + 建任务 |
| 2 | `pdf_to_md` | 10 → 30 | MinerU 主路径；失败降级 pdfplumber（`mineru_pdfplumber`） |
| 3 | `md_img` | 30 → 40 | 图片抽出入库 + MD 产物落存储（重试续跑的依据） |
| 4 | `split` | 40 → 55 | 标题层级切分 + 长切短合 |
| 5 | `embedding` | 55 → 95 | BGE-M3 分批推理，**每批都写进度**（40 个点是实测最慢的一段） |
| 6 | `milvus` | 95 → 100 | 先 `delete(doc_id==)` 再 `insert`，幂等重建 |

> **`embedding` 阶段里还藏着一件容易误判的事**：进程**首次**用到向量化时会加载
> BGE-M3，那是一次 **15~40 秒的同步阻塞调用**。此时任务进度会**停在 55% 不动**，
> 看起来像卡死。所以加载过程现在会打进度（`app/core/progress.py`）：
> 日志每 5 秒一行心跳 + 阶段打点，`/health` 也会进入 `loading` 态并给出已用秒数。
> 实测本机 39.6 秒的加载里 **~26 秒花在 `import torch`**、权重加载只占 ~3 秒——
> 这也是"为什么第一次导入特别慢"的答案（第二次起模型常驻，导入只要几秒）。
> 详细命令见 `docs/测试教程.md` §15.3。

### 5.2 失败 / 超时 / 取消 / 重启

| 情形 | 处置 | 码 |
|---|---|---|
| 阶段内异常 | `status=failed` + `error={stage,code,message}`，**保留中间产物** | `IMP-4001`~`IMP-4005` |
| 插入 0 条切片 | **当失败处理**（`insert` 对空列表返回 0 且不报错） | `IMP-4004` |
| 切分为空 | **当失败处理**（否则得到"导入成功但搜不到"的假可用） | `IMP-4001` |
| 超时（心跳 > `import.timeout_min`） | 看门狗改判 `timeout` | `IMP-4006` |
| 服务重启 | 启动补偿：`pending/running` → `failed`，**不自动重排** | `IMP-5003` |
| 取消 | 阶段边界生效；已插切片保留但置 `enabled=false` | `IMP-3002` |

**看门狗与启动补偿刻意分开**：前者看心跳（"很慢"≠"坏了"），后者无条件
（进程刚起来，无法区分"刚挂上"与"早就死了"）。合并会让慢任务被误报成"服务重启中断"，
把排查方向引到根本不存在的重启记录上。

## 六、三条设计主线（为什么这么做）

### 6.1 归一化是唯一能把复杂度关在门里的做法

四种输入 → 一份 Markdown。若让切片器分辨格式，"标题层级从哪来"在每个格式里
答案都不同，切分逻辑要写四套。所以 `parser.py` 是**唯一**知道格式差异的地方。

三条兜底路径都**必须留痕**（`degraded[]`），因为它们解析出来的 Markdown 必然丢东西：

| 输入 | 主路径 | 兜底 | 降级标记 | 损失 |
|---|---|---|---|---|
| `.pdf` | MinerU 4.0.6 | pdfplumber 0.11.10 | `mineru_pdfplumber` | 版式 / 表格结构 / 图片来源 |
| `.docx` | mammoth | python-docx | `mammoth_python_docx` | 用"手工加粗"伪装的标题认不出来 |
| `.md` / `.txt` | 直读 | — | — | 无 |

**兜底也失败就硬失败**（`IMP-4001`），**绝不返回空 Markdown 让流水线继续**——
那会得到一篇"零切片但导入成功"的文档，界面上是绿的、问答里永远搜不到它。

### 6.2 切片从写入到"文档完成"之间绝不可检索

Spec §2.6 说 `enabled` 初值 = 台账 `status`（`auto_enable=true` 写 `true`）。
实现上**一律先写 `false`**，由 `mark_import_done()` 在最后一步统一同步：

- 两者语义等价（导入完成那一刻的值就是 `auto_enable` 决定的）
- 但后者关掉了"半截切片可被召回"的窗口 —— 而 §3.5 R-04 对取消的要求
  恰恰是"**绝不允许**半截切片被召回"

配套的调用顺序是硬要求：`store_chunks()` **必须**早于 `mark_import_done()`。
反过来 → 同步的是 0 条切片，文档却是 `enabled`，症状是"文档绿的、问答搜不到"，
而且**再也自愈不了**。

### 6.3 导入绝不能阻塞问答（AD-01 + AD-09）

- MinerU 与 BGE-M3 都是**同步阻塞**调用 → 一律 `asyncio.to_thread`
- 并发闸门 `Semaphore(import.concurrency)`，**GPU 不可用时自动降为 1**
  （CPU 推理占满所有核心，两个并发会让问答明显劣化）
- 闸门**惰性创建**：`Semaphore` 必须绑定当前事件循环，模块级常量在 import 时
  创建会绑到别的 loop，一 await 就报 "attached to a different loop"
- 后台任务用 `asyncio.create_task` + 服务内 `_running` 表**拿住强引用**
  （`asyncio` 只持弱引用，"任务莫名其妙停在 pending"的经典原因）

### 6.4 本轮修掉的两个真 bug（都不是测试能直接告诉你的）

| # | bug | 症状 | 根因与修法 |
|---|---|---|---|
| 1 | **`lifespan` 从未连接 Milvus / MinIO** | 早期骨架把它们写死成 `not_configured`，看着"无害"；04 落地后启动补偿直接抛 `MilvusUnavailable` → **服务起不来**（只有"真起 uvicorn"那条 e2e 用例抓到）。更隐蔽的是 `set_chunks_enabled` 每次都走"未连接 → 0 条 + WARN"分支，于是"停用文档"**看起来成功、切片却仍可召回**（最危险的越权形态） | `lifespan` 补 `milvus.connect()` / `minio_store.connect()`（**非 fail-fast**，只记 ERROR）；`/health` 改成真实三元探测 |
| 2 | **E01 集合缺 4 个切分锚点字段** | `title` / `parent_title` / `file_title` / `part` 是 Spec §2.1 的显式字段，早期骨架只建了 6 个 → 切片预览拿不到标题，06 的引用溯源卡片无从渲染 | 补齐字段并**重建集合**（当时无业务数据）；抽 `ALL_FIELDS` 常量给 `set_enabled` 的 read-modify-write 用——`upsert` 是整实体替换，少取一个字段就会把它**悄悄写成空值** |
