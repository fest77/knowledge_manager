> 🔴 **三条 Milvus API 的实测结论**（都是"不报错但结果错"的类型，务必记住）：
>
> 1. **`AsyncMilvusClient` 没有 `update` 方法**（pymilvus 3.0.1 实测只有 `upsert`）。
>    所以"改一个字段"必须走 **`query` 全实体 → 改 `enabled` → `upsert` 回去**三步。
>    两个连带约束：**不能只传 `enabled`** 去 upsert（会把 `doc_id`/`content`/向量全清空）；
>    **必须带 `chunk_id`**（自动主键），否则会插出**新**切片而不是改旧的。
> 2. **`insert` / `upsert` / `delete` 之后必须 `flush()`**。不 flush 时
>    `query(count(*))` 返回 **0**，而插入接口**本身不报错**——症状是"导入显示成功、
>    切片数却是 0"，几乎一定会被误判成"向量没写进去"。这一条让 6 个用例同时红，
>    是它们把根因逼出来的。
> 3. **`content` 的正文默认 `enabled=false`**：文档要经 03 的 `toggle` 显式启用才对外可见；
>    若默认 true，"导入中就已经能被搜到"，答案会引用一篇半成品。

## 3.10 端到端用户旅程发现并修复的 3 个真 bug（**2026-09-25**）

**为什么单模块测试全绿、串起来却炸**：`pytest` 走 `ASGITransport`（进程内直连）且把
Milvus/MinIO 全部打桩，"向量库到底怎么答的"从来没被验过；`acceptance_moduleXX.py`
只覆盖各自模块的接口契约。于是下面这三个 bug 全都通过了 656 个用例。

| # | 症状（用户视角） | 根因 | 修法 |
|---|---|---|---|
| 1 | **问什么都说"知识库暂无相关内容"**：看板召回/拦截恒为 0、缺口识别 0 条、FAQ 也挖不出有效候选 | `MilvusStore.search()` 没传 `anns_field`，而 E01 的集合有**两个**向量字段（稠密 + 稀疏占位）→ 每次检索都 `code=65535 multiple anns_fields exist` | `search(anns_field=F_DENSE)`；`tests/test_infra_module04.py` 加护栏 |
| 2 | **候选审核永久失败**：`FAQ-3004 关联知识单元不存在或已删除：None`，FAQ 一条也发不出去（缓存恒空） | ① `search()` 的 `output_fields` **漏了 `chunk_id`** → `qa_logs` 三列表里 `chunk_id` 全是 `null`；② 07 的 `_doc_ids_of()` 把 `str(None)` 当文档号，产出 `related_docs=["None"]` 这个假文档号 | `output_fields` 补 `F_CHUNK_ID`；`_doc_ids_of()` 改为**经 `recalled_chunks` 建 `chunk_id→doc_id` 映射**再按放行集合过滤，并统一丢掉 `None/"None"/"null"`；`_read_logs` 补投影 `recalled_chunks` |
| 3 | 审计列表的 `actor_name` **恒为空**（日志里一条 WARNING） | `audit_service._lookup_names()` 调 `org_service.real_names_of()`，而 02 里**没有这个函数**（只有 `audit_repo` 里有）→ 每次回填都抛 `AttributeError` 被吞成降级 | 在 `org_service` 补 `real_names_of()`（经 `org_repo.find_users_by_ids`，**只返回姓名**，绝不递出 `password_hash`） |

**第 2 个 bug 的教训值得单独记一笔**：07 的单测夹具把 `allowed_chunks` 写成
`[{"chunk_id": 1, "doc_id": doc}]`，而 06 的真实产出是**切片主键列表**——夹具与生产不一致，
于是"切片号被当文档号"这条链式故障一路绿灯。现已补两条回归护栏：
`test_doc_ids_of_matches_the_real_qa_log_shape`（真机形状）与
`test_mined_candidate_with_real_log_shape_can_be_approved`（真形状下能审过）。

## 3.11 加载进度可见 + 测试提速（**2026-09-28**）

### 3.11.1 问题：40 秒的静默加载 = 看起来像卡死

用户的原始问题：*"`pytest -q` 在 PyCharm 终端里为什么加载那么慢？"*
实测拆开看，慢是**两件不同的事**叠加：

| 环节 | 实测 | 说明 |
|---|---|---|
| 每个 `client` 夹具用例 | **~0.95s** | `drop_collections` 0.03s + `write_seed` **0.85~0.92s**（其中 **bcrypt 12 轮 = 0.30s**，其余是 ~125 次远端 Mongo 往返） |
| BGE-M3 首次加载 | **39.6s** | 其中 **`import torch` / `sentence-transformers` ≈ 26s**、权重加载 ≈ 3s、fp16 转换 ≈ 2.6s、自检 ≈ 0.4s |
| 全量 664 例 | **14.2 分钟**（秒表实测） | 439 个用例带夹具（≈6.5 分钟）+ 真模型文件 ~48s + 真 Milvus 往返（`flush` 实测 3~11s 不等）+ 真 uvicorn；**同一套代码换天跑会差 2~3 分钟**，差异来自共用虚拟机的负载 |

**结论**：不是 PyCharm 的锅（终端里跑的也是同一个 Python 进程），
而是"这是一套**集成**测试：真库 + 真模型 + 每个用例都清库重灌种子"。

### 3.11.2 改动一：加载进度可见（`app/core/progress.py`）

`Progress` 上下文管理器 = **阶段打点 + 心跳线程**（每 5 秒一行"仍在进行（已用 Ns）"），
退出时打一行总耗时；心跳线程是 daemon，且**吞掉所有与显示相关的异常**。
BGE-M3 与 reranker 的 `load()` 都接上了它，并且：

- `/health` 新增**第四态** `loading`（配 `import.embedding_loading_seconds` 递增秒数），
  不再把"正在加载"谎报成 `not_configured`；
- 进度同时走**日志**（受级别控制，供落盘）与 **stderr 回声**（`KM_PROGRESS=1` 或 TTY 时），
  这样测试进程把 `KM_LOG_LEVEL` 压到 `WARNING` 时进度依然看得见；
- 顺手修掉一个真浪费：`unload()` 在**没加载**时也会 `import torch` + `empty_cache()`，
  首次 `import torch` 实测 **8.3 秒**（`test_embedding_service.py` 里就白等了 8.27 秒）。

实测（真机 cuda:0）：

```
[BGE-M3 加载] 开始加载；首次约 15~40 秒，之后常驻显存
[BGE-M3 加载] 解析设备（已用 0.0s）
[BGE-M3 加载] 仍在进行：导入 sentence-transformers / torch（已用 10.0s）   ← 每 5 秒一行
[BGE-M3 加载] 读取模型权重（D:\…\bge-m3）（已用 32.0s）
[BGE-M3 加载] 转换为半精度（fp16）（已用 38.6s）
[BGE-M3 加载] 完成（共 39.6s）
/health 期间：embedding_model=loading、embedding_loading_seconds 1.8 → 38.6 → 之后 ok
```

### 3.11.4 一条必须记住的纪律（**踩过两次**）

**同一个项目目录里，一次只跑一个 pytest 进程**。除了共用测试库 `kb001_test` 会互相清库，
更隐蔽的是 pytest 的 `tmp_path`：新会话启动时会 GC 掉旧的 `basetemp` 目录，
于是**正在跑的那个会话**里 `tmp_path` 凭空消失，症状是解析类用例报 `FileNotFoundError`
（本次就这么误报过一次，看起来像代码 bug，其实是并发）。
