# 审计存储层护栏（append-only 的第三层）

> 模块：10 审计日志
> 对应验收：**AC-10-03**
> 对应规格：`Spec_coding_步骤/04_模块Spec/10_审计日志.md` §2.1「append-only 的存储层强制」

## 1. 为什么需要这一层

模块 10 用**三层**落实"审计不可改"，缺一层都不完整：

| 层 | 措施 | 谁能绕过 | 由谁保证 |
|---|---|---|---|
| 接口层 | `/api/v1/audit/*` 只有 GET；任何写方法一律 `AUD-2003` | 能改代码的人 | 代码 + `AC-10-02` 用例 |
| 服务层 | `audit_repo` **不提供** `update` / `delete` 方法 | 能改代码的人 | 代码 + 单测断言 |
| **存储层** | 应用账号对 `audit_logs` 只有 `insert` + `find` | **没人**（除库管理员） | **本文档的部署配置** |

前两层是**约定**，第三层才是**能力边界**。演示时最容易被问"你怎么保证
审计不被改"，这一条是唯一有说服力的答案，而它的成本几乎为零。

## 2. 自检

```powershell
.venv\Scripts\python.exe scripts\audit_storage_guard.py
```

脚本会报告：

- 当前 MongoDB 的 `security.authorization` 状态
- 当前连接是否已认证账号
- 若已开启鉴权：**实际试一次** `updateOne`，看是否被 `not authorized` 拒绝
- 若未开启鉴权：明确说明"本环境无法强制执行该验收项"，并打印下面的命令

## 3. 部署配置（校验/生产环境执行）

```javascript
// 1) 建一个"只插只查"的审计角色（对业务库生效）
use kb001
db.createRole({
  role: "km_audit_append_only",
  privileges: [
    { resource: { db: "kb001", collection: "audit_logs" },
      actions: [ "insert", "find" ] }
  ],
  roles: []
})

// 2) 授权给应用账号（把 <appUser> 换成应用真正使用的账号）
db.grantRolesToUser("<appUser>", [ { role: "km_audit_append_only", db: "kb001" } ])

// 3) 用该账号连库后验一遍：下面两条**必须报 not authorized**
db.audit_logs.updateOne({}, { $set: { reason: "tampered" } })
db.audit_logs.deleteOne({})
```

> **注意**：`insert` + `find` 之外**不要**给 `update` / `remove` / `drop`。
> 也不要在 `audit_logs` 上建 TTL 索引（保留策略是**永久**，`DEC-10-7`）。

## 4. 本项目的实测结论（2026-09-24）

| 项 | 结论 |
|---|---|
| 目标 | `mongodb://192.168.6.170:27017` / `kb001` |
| `security.authorization` | **disabled** |
| 已认证账号 | 无 |
| 接口层（AC-10-02） | ✅ 已通过（4 种写方法 × 2 个路径全部 `AUD-2003`） |
| 服务层（DEC-10-2） | ✅ 已通过（单测断言仓储无 update/delete 方法） |
| **存储层（AC-10-03）** | ⚠️ **当前环境无法强制执行**：该 MongoDB 未开启访问控制，没有账号体系，因此无法把 `audit_logs` 限制成 `insert + find` |

**这不是"跳过验收"，而是环境的已知边界**：交付时按第 3 节配置完，
重跑 `scripts/audit_storage_guard.py`，脚本会在第 3 步拿到 `not authorized`
并把结论改为"护栏成立 ✔"。届时 AC-10-03 才算完整通过。
