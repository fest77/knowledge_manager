## 4. 接口逐条验证

> **下面的命令全部用 PowerShell 语法实测通过。**
> ⚠️ 一个高频坑：`curl.exe -d "{\"k\":\"v\"}"` 这种**反斜杠转义会被 PowerShell 吞掉**，
> 服务端收到非法 JSON 返回 `SYS-1001`。**正确写法**是单引号 + 无反斜杠：
> `curl.exe ... --data-raw '{"k":"v"}'`，或直接用 `Invoke-RestMethod`。

## 6. 深度验证：三个"应该被抓住"的场景

这三个场景是**故意设计成容易出错**的，用来验证实现是否真的严谨。

### 6.1 停用账号后，已签发的令牌必须立即失效

```powershell
# 终端 A：登录拿令牌
$t = (Invoke-RestMethod -Uri http://127.0.0.1:8102/api/v1/auth/login -Method Post `
      -ContentType "application/json" `
      -Body '{"username":"wangqiang","password":"Demo@12345"}').data.access_token
Invoke-RestMethod -Uri http://127.0.0.1:8102/api/v1/auth/me -Headers @{Authorization="Bearer $t"}
# → 正常返回
```

```powershell
# 终端 B：把该用户停用
.venv\Scripts\python.exe -c "from pymongo import MongoClient; c=MongoClient('mongodb://192.168.6.170:27017'); c['kb001']['sys_users'].update_one({'username':'wangqiang'},{'$set':{'status':'disabled'}}); print('已停用')"
```

```powershell
# 终端 A：同一个令牌再请求
Invoke-RestMethod -Uri http://127.0.0.1:8102/api/v1/auth/me -Headers @{Authorization="Bearer $t"}
# → 期望：401 AUTH-2002「账号已停用」
```

**恢复**：`.venv\Scripts\python.exe scripts\seed.py`（重新灌种子即恢复）

> **原理**：JWT 里**只放身份不放权限**，所以每次请求都会查库校验 `status`。
> 如果这里没被拦住，说明有人把角色/权限塞进了 token —— 那会破坏"权限即时生效"的主张。

### 6.2 越权订阅 SSE 流（存量 `sse_util` 的真实缺陷）

本切片还没实现 SSE，但**相同的归属校验思路**已在中间件体现：
用 A 的令牌只能拿 A 的数据。可用 6.1 的方式验证：
用 `wangqiang` 的令牌访问时，返回的 `user_id` 必须是 `U000003`，**不能**是别人。

### 6.3 索引自愈（升级路径）

```powershell
# 故意造一个"大小写敏感"的旧索引，模拟从旧版本升级
.venv\Scripts\python.exe -c "from pymongo import MongoClient; col=MongoClient('mongodb://192.168.6.170:27017')['kb001']['sys_users']; col.drop_index('uq_username'); col.create_index('username', unique=True, name='uq_username'); print('已造旧索引')"
# 重启服务
# 期望日志出现：索引 uq_username 的 collation 与期望不符（现有=None 期望={'locale': 'en', 'strength': 2}），先删除后重建
# 然后大小写不敏感登录恢复正常
```
> 这条覆盖一个很容易漏的坑：Mongo 的 `create_index()` 对**同名同键**的索引是幂等的，
> **collation 变了它不会重建**。测试库每次清库重建所以看不出问题，
> 正式库会保留旧索引 —— 典型的"测试全绿、线上错的"。

## 8. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `ConfigError: 缺少必需配置 MONGO_URL` | `.env` 不在项目根 | 确认 `.env` 存在；或用 `KM_ENV_FILE` 指向它 |
| `ConfigError: 配置 JWT_SECRET 长度不足 32` | PyJWT 2.14 要求 HS256 密钥 ≥32 字节 | 在 `.env` 写入 ≥32 字节随机串 |
| `[Errno 10048]` 端口被占 | 有残留 uvicorn 子进程 | 见 §3 的排查命令 |
| `缺少必需配置` 出现在 pytest | pytest 工作目录不是项目根 | `cd` 到项目根再跑 |
| 登录返回 `SYS-1001 JSON decode error` | curl 的 JSON 反斜杠被 PowerShell 吞了 | 用单行单引号写法，见 §4 开头的提示 |
| **`ERR_CONNECTION_REFUSED`（127.0.0.1 拒绝连接）** | **服务没在跑**（最常见） | 另开终端执行 ``.\scripts\run_server.ps1`，看到 `Uvicorn running` 再刷新 |
| 前端页面打不开 | 用了 `/` 而不是 `/ui/` | 访问 `http://127.0.0.1:8102/ui/` |
| `pytest` 报 `拒绝在非测试库上跑测试` | 环境变量把库名改掉了 | 不要在跑测试前设 `MONGO_DB_NAME=kb001` |

### 15.3 加载慢的时候怎么办（**进度是可见的**）

首次用到向量化/重排模型时会有一次 **15~40 秒**的阻塞加载。这段过程**有进度输出**，
不需要靠猜：

```powershell
# ① 应用侧（uvicorn 控制台）：启动后第一次提问 / 导入时，日志每 5 秒一行心跳
#    [BGE-M3 加载] 开始加载；首次约 15~40 秒，之后常驻显存
#    [BGE-M3 加载] 解析设备（已用 0.0s）
#    [BGE-M3 加载] 仍在进行：导入 sentence-transformers / torch（已用 10.0s）
#    …（每 5 秒一行）…
#    [BGE-M3 加载] 读取模型权重（D:\ai_models\…\bge-m3）（已用 32.0s）
#    [BGE-M3 加载] 转换为半精度（fp16）（已用 38.6s）
#    [BGE-M3 加载] 完成（共 39.6s）
#    ★ 实测：39.6 秒里 **~26 秒花在 `import torch`**，权重加载只占 ~3 秒
#      ——这是"看起来卡住"的真正原因，也是本机最值得优化的那一段

# ② 接口侧：加载期间 /health 进入第四态（而不是谎报 not_configured）
curl.exe -s http://127.0.0.1:8102/health
# 期望：dependencies.embedding_model = "loading"
#       import.embedding_loading_seconds = 递增的秒数（如 12.4）
# 加载完成后：embedding_model = "ok"、embedding_device = "cuda:0"
# （reranker 同理：dependencies.reranker_model 与 import.reranker_loading_seconds）

# ③ 测试侧：pytest 默认把日志压到 WARNING + 捕获输出，所以要两样都给上
$env:KM_PROGRESS = "1"      # 强制把进度同时回声到 stderr（不受日志级别影响）
.venv\Scripts\python.exe -m pytest tests\test_embedding_service.py -q -s
#    -s 关掉 pytest 的输出捕获；不加 -s 时进度会被 capture 吞掉（pytest 的行为）
#    交互式终端里也可以不设 KM_PROGRESS：stderr 是 TTY 时会自动回声
```

### 15.4 开发期常用的"快跑"命令（别每次都跑全量）

```powershell
# 全量（664 例，实测 12~15 分钟，含真 Milvus / 真模型；秒表卡过 854s）
.venv\Scripts\python.exe -m pytest -q

# 只跑本次改动的模块
.venv\Scripts\python.exe -m pytest tests\test_metric_service.py -q

# 按名字挑
.venv\Scripts\python.exe -m pytest -q -k "uv or 降采样"

# 跳过"重"文件（真模型 / 真 Milvus / 起 uvicorn），做快速回归
.venv\Scripts\python.exe -m pytest -q `
  --ignore=tests/test_embedding_service.py `
  --ignore=tests/test_infra_module04.py `
  --ignore=tests/test_chunk_store.py `
  --ignore=tests/test_e2e_smoke.py
```

> **测试里 bcrypt 用的是 4 轮**（`tests/conftest.py` 设 `BCRYPT_ROUNDS=4`）：
> `client` 夹具每个用例都要灌一次种子口令，12 轮实测 ~300ms × 439 个用例 ≈ 2 分多钟；
> 降到 4 轮后校验路径（`$2b$` 前缀 / verify 往返 / 错口令拒绝）完全一样，
> **只影响测试进程**（已核对全仓没有用例断言轮数）。
> 实测：`test_auth_integration.py` 从 **29.1s → 17.9s**。

> ⚠️ **一次只跑一个 pytest 进程**（这条踩过两次，务必记住）：
> 1. 所有用例共用测试库 `kb001_test`，并发会互相 `drop_collection`，
>    症状是"随机几个用例集体失败"；
> 2. 更隐蔽的是 pytest 的 `tmp_path` —— 新会话启动时会 **GC 掉旧的 `basetemp` 目录**，
>    于是**正在跑的那个会话**里 `tmp_path` 突然消失，症状是解析类用例报
>    `FileNotFoundError`（看起来像代码 bug，其实是同一个项目被并发跑了两次）。
> 想边跑全量边做别的验证？**等全量跑完再动**，别在同一个项目目录里再起一个 pytest。
