| GET/POST | `/api/v1/categories` | `doc:read` / `doc:category` | 分类树 / 新建 |

| POST | `/api/v1/categories/recount` | `doc:category` | 文档计数重算 |

### 3.1 两条路由顺序是硬要求

| 必须在前 | 必须在后 | 写反的后果 |
|---|---|---|
| `/docs/dedup-check` | `/docs/{doc_id}` | `dedup-check` 被当成 `doc_id` → 预检报"知识单元不存在" |
| `/categories/recount` | `/categories/{category_id}` | `recount` 被当成 `category_id` → 404 |

### 3.2 供 04 / 05 / 08 调用的内部契约（§3.8）

| 方法 | 调用方 | 约束 |
|---|---|---|
| `create(...)` | 04 | 支持**预分配编号**（`doc_id` / `doc_no`）——因为 04 的落盘顺序是"先落盘再建台账"，而对象键是 `{doc_id}/...` |
| `mark_import_done(doc_id, chunk_count, char_count, *, enable=True)` | 04 | `enable=False` 时只写 `import_status=done`，**不动 `status`**（`auto_enable=false` 路径） |
| `mark_import_failed` / `update_import_status` / `update_storage` | 04 | 04 禁止直连写 `kb_documents` |
| `update_permission_summary` | 05 | 05 不得直接写台账 |
| `create_placeholder` | 08 | 无文件的待补充单元（`file_hash = sha256("placeholder:...")`） |
| `resolve_by_hash` / `find_by_hash` | 04 | 去重决策 / 只读取记录 |

## 四、数据模型

### 4.1 E04 `kb_documents` 的 10 个索引

`deleted_at` / `file_hash`（**部分唯一索引，`partialFilterExpression: deleted_at=null`**）/
`category_id` / `status` / `title` 文本 / `created_at` 等。

**部分唯一索引是"软删除后可重导"的前提**（OQ-04-10）：普通唯一索引会在
"同哈希文档被软删除"后永久阻塞重导，而业务上"删掉再传一份"是最常见的操作。

`assert_dedup_index_ready()` 在每次建台账前自检索引是否就绪，缺了就 **fail-closed**
报 `DOC-4004`——**不能"先建了再说"**：没有唯一索引，同哈希并发上传会产生两条台账，
而两条台账指向同一份存储对象，后续的删除 / 回填会互相打架。

### 4.2 E05 `kb_categories` 的物化路径

字段：`name` / `parent_id` / `path`（名字路径）/ `path_ids`（编号路径）/ `level` / `doc_count` / `sort`。

移动分类要重算**所有子孙**的 `path` / `path_ids` / `level`（AC-03-14），
级联失败报 `DOC-5002`。同级重名靠唯一索引兜住（根分类用 `null` 哨兵参与索引，AC-03-13）。

关键断言（都是"看起来对、其实错"的高危点）：

| 断言 | 挡住什么 |
|---|---|
| 列表不因角色/部门而变，响应中无 `allow`/`denied` 字段 | 把四维权限偷偷做进列表（ER-03 越界） |
| `page_size=201` → `DOC-1001`（**不静默截断为 200**） | 静默截断会让调用方以为拿全了 |
| 停用 → 切片 `enabled` 全 false 且**条数不减** | 用"物理删切片"实现停用（不可恢复） |
| 切片服务异常 → `DOC-4003` 且文档状态**保持原值** | "文档已停用、切片仍可召回"的越权形态 |
| 循环移动 → `DOC-3008`（检查方向：`dept/分类自身` 是否在新父的 `path_ids` 里） | 方向写反会导致"能把自己移到自己的子树下" |
| 删掉 `file_hash` 唯一索引 → `DOC-4004` | fail-closed 被绕过 |

## 六、03↔04 的连续批次约定（模块 04 落地时回填）

总纲 §4.2 约定：**03 停用 / 软删 / 恢复文档时，必须同步切片的 `enabled`，
而 03 自己不许连 Milvus**。04 落地后回填如下：

| 项 | 实现 |
|---|---|
| 调用点 | `DocService.toggle()` / `soft_delete()` / `restore()`，**统一走 `_sync_chunks()`** |
| 顺序 | **先同步切片、再改文档状态**（避免"改了再回滚"的中间窗口） |
| 失败 | `ChunkStoreError` → `DOC-4003`，**文档状态不变** |
| 收敛点 | `ImportService.set_chunks_enabled()` → `chunk_store.set_chunks_enabled()`（E01 的唯一写入口） |
| 用例 | `test_ac_03_09_disabling_a_doc_disables_its_chunks`（真 Milvus 往返）<br>`test_ac_03_10_chunk_sync_failure_keeps_document_unchanged`（注入异常） |
