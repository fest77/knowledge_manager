## 三、接口契约

### 3.1 `GET /api/v1/audit/logs` — 审计流水（四维筛选 + 分页）

| 项 | 内容 |
|---|---|
| 功能权限 | `audit:read` |
| 入参 | `action`（逗号分隔可多值，别名展开）· `actor`（`user_id`/`username`/`system`）· `target_type` · `target_id` · `start_ts` · `end_ts` · `outcome` · `actor_role` · `page` · `page_size` · `sort` |
| 出参 | `{ items:[...], total, page, page_size, degraded }` |
| 列表字段 | `audit_id` `ts` `actor` `actor_name` `actor_role` `action` `action_name` `target_type` `target_id` `target_name` `changed_fields` `reason` `outcome` `ip` `snapshot_state`（**不含** `before`/`after`） |

### 3.2 `GET /api/v1/audit/logs/{log_id}` — 单条详情

| 项 | 内容 |
|---|---|
| 功能权限 | `audit:read` |
| 出参 | 在列表字段之上 + `before` / `after` / `redacted_keys` / `extra` / `trace_id` / `ua` |
| 规则 | `log_id` 先校验格式（`AUD-1003`）再查库（不存在 `AUD-3001`）；`snapshot_state=dropped` **不是错误**，200 + `before/after=null` |

### 3.3 `GET /api/v1/audit/logs/export` — 导出（流式）

| 项 | 内容 |
|---|---|
| 功能权限 | `audit:export` |
| 入参 | §3.1 的全部筛选参数 + `format`（`csv` 默认 / `json`） |
| 出参 | 附件流：`text/csv; charset=utf-8` 或 `application/json`，另有 `X-Audit-Rows` 响应头回报行数 |
| 上限 | 命中 > 50000 → `AUD-1005` |

**路由声明顺序是硬要求**：`/logs/export` 必须声明在 `/logs/{log_id}` **之前**，否则 FastAPI 会把 `export` 当成一个 `log_id` 匹配掉。

**CSV 的 15 列（固定，不随筛选变化）**：
`ts, actor, actor_name, actor_role, action, action_name, target_type, target_id, target_name, changed_fields, reason, outcome, ip, before, after`
（`ts` 为本地 `YYYY-MM-DD HH:MM:SS`；`changed_fields` 用 `|` 连接；`before`/`after` 压成单列 JSON）

**调用方义务（写进契约）**

| # | 义务 |
|---|---|
| D-01 | **不要** `try/except` 包裹 `record()`，也**不要**用返回值决定业务响应 |

## 六、三条设计主线（为什么这么做）

### 6.1 `record()` 永不抛异常（DEC-10-1）

| 若抛异常的后果 | 说明 |
|---|---|
| **业务被审计拖死** | 「重置了密码但接口报错」是荒谬的：密码已经改了，用户却看到失败，会重复操作 |
| 事务语义被污染 | 审计是事后凭证，不该参与业务成败判定 |
| 与 01/02/05 的降级约定冲突 | 三份 Spec 都写了「审计失败只记 ERROR，不阻断业务」 |

**降级三段式**：Mongo 失败 → 立即重试 1 次（退避 50ms）→ 本地 JSONL 补偿文件 → CRITICAL + `/health` 置 `degraded`。
连续 5 次失败 → 熔断 60 秒，期间**直接**落补偿文件（省掉每次业务 500ms 的等待）。

> 一句话：审计**可以丢**（有补偿与显式告警），但**绝不可以拦住业务**。

### 6.2 脱敏失败 → 丢弃整个快照（DEC-10-5）

脱敏器的失败是**未知的失败**——你无法保证它只是没替换，还是替换了一半。
此时唯一安全的动作是**放弃这段数据**，而不是赌它没问题。与 05 模块的 fail-closed 同源。

**执行顺序**（都在写入路径上、各做一次）：diff-only → **脱敏** → 16 KB 截断 → **再脱敏**。
先脱敏一遍是因为大文本/向量必须先降级，否则量体积时会被几 MB 正文拖死；
第二遍是"入库前最后一道闸"，保证任何路径产出的值都被检查过（也是 §2.3 C 的字面要求）。

**摘要键豁免**：`sha256` / `spool_id` / `file_hash` 等的值**天然**是 32~64 位十六进制，
若被"疑似密钥"规则误杀，截断占位 `{"__truncated__":true,"sha256":"..."}` 就失去可校验性。
所以值正则带 `DIGEST_KEYS` 豁免——这是实现时必须做的一处判断，否则规则会自相矛盾。

### 6.3 append-only 三层

| 层 | 措施 | 谁保证 |
|---|---|---|
| 接口层 | `/api/v1/audit/*` 只有 GET；任意写方法 `AUD-2003` | 代码 + `AC-10-02` |
| 服务层 | `audit_repo` **不提供** `update`/`delete` | 代码 + 单测 |
| 存储层 | 应用账号对 `audit_logs` 只有 `insert`+`find` | **部署配置** → `docs/审计存储层护栏.md` |

**唯一被认可的删除入口**是 `audit_repo.purge_before()`，只由 `scripts/purge_audit.py`
在"先留痕、再归档、显式 `--yes`"之后调用——这样"能删审计"这件事只有一个可被 review 的位置。
